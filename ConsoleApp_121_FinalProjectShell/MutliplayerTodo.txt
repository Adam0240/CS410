# Multiplayer Implementation To-Do: Shared World Sync (2-player online)

Goal:
Implement a 2-player online multiplayer mode for the current Zork/text-adventure project with these exact rules:

- Player 1 hosts the game.
- Player 2 joins from another computer.
- Both players can move independently with no turn-based lock.
- The game world is shared and synchronized.
- If one player changes the world, the other player must see that same change.
- If both players are in the same room, room text must mention the other player.

Critical design rule:
The host is the single source of truth for the entire game state.
The client must never maintain an independent world state that can drift from the host.

That means the host controls and synchronizes:
- player positions
- room contents
- picked up items
- dropped items
- used/consumed items
- unlocked/opened/cleared room states
- any flags that affect gameplay
- player connection status

## Phase 2: Define the network protocol clearly

2. Create a minimal but explicit network message protocol.

The protocol must support:
- join request
- join accepted
- player connected
- player disconnected
- command submission from client to host
- state update from host to client
- room update from host to client
- system/error message
- full snapshot sync from host to client

Important rule:
The client sends player intent.
The host validates, applies, and broadcasts results.

Examples:
- client sends: `go north`
- host decides whether movement is valid
- host updates authoritative state
- host sends updated room/world state back

Do not let the client directly mutate gameplay state on its own.

Host-authoritative shared state must include:
- both players

- each room’s current contents
- room completion/cleared flags
- item ownership/location

- `ConsoleApp_121_FinalProjectShell/People/Character.cs`

Optional new file:

Important implementation rule:
There must be only one authoritative version of:
- where each item is
- whether an item is in a room
- whether an item is in a player inventory
- whether an item has been consumed/used/removed

Example required behavior:
- If Player 1 picks up a key in Room A, Player 2 must no longer see that key in Room A.
- If Player 1 drops the key in Room B, Player 2 must see that key in Room B.
- If Player 1 uses an item that removes it from the world, Player 2 must see that same result.
- If a room state changes, both players must see the changed version.

This is required. Do not implement movement sync only.

## Phase 4: Host-authoritative command handling

4. Route all gameplay-changing commands through the host.

Commands that must be host-authoritative include at minimum:
- `go`
- `take`
- `drop`
- `use`
- any command that changes room state
- any command that changes inventory
- any command that changes puzzle progress
- any command that affects room descriptions or available exits/items

Required flow:
1. player enters command
2. command is sent to host if needed
3. host validates the command
4. host applies the command to authoritative game state
5. host sends back updated results/state
6. both players receive the correct synced view

Files to edit:
- `ConsoleApp_121_FinalProjectShell/Core/Game.cs`
- `ConsoleApp_121_FinalProjectShell/Commands/CommandActions.cs`
- `ConsoleApp_121_FinalProjectShell/Commands/CommandActionRegistry.cs`

Important:
Do not leave `take`, `drop`, or `use` as purely local client actions.
Those must update the shared world through the host.

## Non-negotiable implementation rules

These rules must be followed:

1. The host is the only authoritative source of game state.
2. The client must not apply permanent gameplay changes locally without host approval.
3. The shared map must stay synchronized between both players.
4. Room contents must stay synchronized between both players.
5. Item pickup, drop, and use must stay synchronized between both players.
6. Puzzle/world-state changes must stay synchronized between both players.
7. No duplicated unique items.
8. No room/item desync between players.
9. Single-player mode must continue to work unchanged when multiplayer is not active.
